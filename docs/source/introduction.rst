Introduction
============

GoNetEm is a network emulator: it creates a virtual network on a single Linux
machine, runs real protocol stacks inside it, and lets you shape the links
between them. The topology is described by a small YAML file; the emulator
turns it into Linux resources and keeps them in sync with the project.

Unlike a pure simulator, GoNetEm does not model packets in user space. Nodes
are backed by a real Linux network stack — a Docker container or a bare network
namespace — and every link is a real veth pair. Impairments are applied by the
Linux kernel through `netem` and `tbf` qdiscs, so transport behaviour (TCP
congestion control, retransmissions, queueing) is the behaviour of the kernel,
not of a simplified model. Switching is provided either by a Linux bridge or by
Open vSwitch, and an optional P4 software switch image (bmv2, a userspace data
plane) is available for programmable data plane experiments.

What GoNetEm gives you
----------------------

Reproducibility
   A project is an archive containing the topology **and** the captured node
   configuration files. Opening the same ``.gnet`` file on another host
   recreates the same network, including interface addresses, routes, FRR
   configuration, DHCP/TFTP/BIND data and switch VLANs.

Text-first workflow
   Topologies are YAML, not mouse clicks. They can be reviewed, diffed,
   generated by scripts and versioned in Git. A ``.gnet`` file is a gzipped tar
   archive, so it is a single portable artifact.

Scriptable control plane
   Everything the console does is a gRPC call. Tests and orchestration tools
   can drive the server directly (see :ref:`api`), including batch operations
   designed to keep large topologies fast.

Kernel-accurate QoS
   Per-direction delay, jitter, loss, rate, buffer sizing, burst size, netem
   queue limit and interface transmit queue length are applied with
   ``tc``/netlink semantics (see :ref:`qos`).

Multiple node technologies
   Docker-based hosts, servers, FRR routers, P4 switches, VyOS or your own
   images; Open vSwitch switches; and lightweight pure network-namespace
   nodes for large topologies.

Operational conveniences
   Node consoles, command execution, file copy, packet capture into Wireshark,
   configuration snapshots, project save/extract, image pulling and a
   self-update command.

What GoNetEm is not
-------------------

* It is not a packet-level simulator: there is no discrete-event engine and no
  synthetic clock. Time is real time.
* It is not a multi-host orchestrator: one ``gonetem-server`` drives one Linux
  host. Remote operators connect to that server over gRPC (optionally with
  mutual TLS), but the emulated resources are local to the server.
* It is not a container scheduler: containers are created directly through the
  Docker API with ``--net=none``-like semantics and are attached to the
  emulated topology by moving veth endpoints into their namespaces.

Key concepts
------------

.. list-table::
   :header-rows: 1
   :widths: 22 78

   * - Concept
     - Definition
   * - **Server**
     - ``gonetem-server``, a root daemon exposing the gRPC ``Netem`` service
       and owning all emulated resources.
   * - **Console**
     - ``gonetem-console``, the CLI and interactive client.
   * - **Project**
     - A topology plus its configuration files, exchanged as a ``.gnet``
       archive. The server extracts it to a temporary directory and keeps it
       open until the project is closed. Several projects can be open at once,
       each with a short random identifier.
   * - **Topology**
     - The content of ``network.yml``: ``nodes``, ``links``, ``bridges`` and
       the optional ``mgntnet`` section.
   * - **Node**
     - An emulated device. Three families exist: ``docker.*`` (container),
       ``ovs`` (switch port on the project's Open vSwitch instance) and
       ``namespace`` (bare Linux network namespace).
   * - **Link**
     - A point-to-point veth pair between two node interfaces, identified by
       ``<node>.<ifIndex>`` peers, with optional per-direction QoS.
   * - **Bridge**
     - A Linux bridge on the host that connects selected node interfaces to a
       physical host interface, so the emulated network can reach the outside
       world.
   * - **Management network**
     - An optional Linux bridge with an IP address on the host, giving direct
       SSH/ICMP access to each attached node through a dedicated ``mgnt``
       interface.
   * - **QoS**
     - Per-direction link characteristics: ``delay``, ``jitter``, ``loss``,
       ``rate``, ``buffer``, ``burst``, ``limit`` and ``txqueuelen``.
   * - **Switch console**
     - A command interpreter (``ovs-console.py``) presented when a console is
       opened on an ``ovs`` node; it manages VLANs, STP and bonds.

How it works
------------

The following sequence describes what happens when a project is opened and
started. Implementation details are in :ref:`architecture`.

1. The console reads the local ``.gnet`` file and sends it to the server with
   ``ProjectOpen``. The server extracts the archive into a working directory
   and loads ``network.yml``.
2. Loading validates the topology, creates the node objects (containers are
   created immediately unless ``launch: false``) and builds the in-memory
   link and bridge model.
3. ``TopologyRun`` starts the OVS container if needed, creates the management
   bridge, starts nodes in parallel, creates veth pairs and applies qdiscs in
   parallel, creates bridges and finally configures interfaces and loads node
   configuration files.
4. The console prompt then issues further RPCs: ``status``, ``exec``,
   ``console``, ``capture``, ``start``/``stop`` and so on. Runtime topology
   changes (``NodeAdd``, ``NodeDel``, ``LinkAdd``, ``LinkDel``,
   ``LinkUpdate``) are applied live and can be written back to
   ``network.yml``.
5. Closing the project (``quit``) removes containers, namespaces, veth pairs,
   bridges, the management network and the OVS instance, then deletes the
   temporary directory.

Node technologies
-----------------

.. list-table::
   :header-rows: 1
   :widths: 16 24 60

   * - Family
     - Type
     - Emulated device
   * - Docker
     - ``docker.host``
     - End-user machine: ping, traceroute, hping3, iperf/iperf3, tcpdump,
       Scapy, DHCP client, TFTP client, BIND utilities, a QUIC client and
       multicast traffic generators.
   * - Docker
     - ``docker.server``
     - Service machine: HTTP (lighttpd), DHCP server and relay, TFTP, DNS
       (BIND), FTP, NTP, plus a QUIC server.
   * - Docker
     - ``docker.router``
     - Router running FRR (zebra, bgpd, ospfd, pimd, ldpd, pbrd, bfdd, vrrpd).
   * - Docker
     - ``docker.p4sw``
     - P4 software switch (bmv2 ``simple_switch_grpc``) with a basic IPv4
       forwarding pipeline.
   * - Switch
     - ``ovs``
     - Layer-2 switch implemented as an Open vSwitch bridge inside one shared
       container per project.
   * - Namespace
     - ``namespace``
     - Lightweight node with a Linux network namespace only; shares the host
       filesystem and process namespace.
   * - Custom
     - ``docker.<type>``
     - Any image declared in ``docker.extraNodes`` in the server configuration
       (VyOS is the documented example).

See :ref:`nodes` for the configuration reference, :ref:`docker-images` for the
image catalogue and :ref:`internals-nodes` for the implementation.

Feature summary
---------------

.. list-table::
   :header-rows: 1
   :widths: 34 66

   * - Capability
     - Summary
   * - Topology as code
     - YAML with nodes, links, bridges, management network and per-link QoS.
   * - Live topology changes
     - Add/delete nodes and links, change QoS and interface state without
       restarting the project. Batched RPCs amortise locking and namespace
       switches.
   * - Configuration persistence
     - Per-node type, the server captures configuration files and folders
       into the project. ``save`` stores them; ``viewConfig`` and ``config``
       expose them.
   * - QoS
     - ``netem`` delay/jitter/loss plus ``tbf`` rate shaping, with BDP-based
       buffer sizing, burst control, queue limits and ``txqueuelen``.
   * - Routing
     - Typed batch route installation through netlink (``RouteInstall``) in
       addition to arbitrary command execution (``exec``/``NodeRun``).
   * - Capture
     - Streams ``tcpdump`` output from any interface to a local Wireshark.
   * - File transfer
     - Stream upload/download between the operator machine and nodes.
   * - Consoles
     - xterm-based consoles with a configurable terminal template; switch
       console for OVS; ``bash``/``vtysh``/``simple_switch_CLI`` for containers.
   * - Multi-user access
     - Optional mutual TLS between console and server (:ref:`tls`).
   * - Self-update
     - ``gonetem-console update`` pulls, builds and installs a new server
       version (:ref:`internals-update`).
   * - Container hygiene
     - ``gonetem-console clean`` prunes gonetem containers no open project
       owns.

Requirements at a glance
------------------------

Server host:

* Linux with network namespaces, veth, netlink, ``tc`` (``sch_netem``,
  ``sch_tbf``) and ``ethtool`` ioctl support.
* Docker Engine.
* Root privileges (the service runs as root).
* ``nsenter`` (util-linux) and ``tar`` for node command execution and
  configuration archiving.

Operator workstation:

* ``gonetem-console`` (Linux, or built for the platform).
* ``xterm`` for node consoles and ``wireshark`` for packet capture, when those
  features are used.

Details and the supported build targets are in :ref:`installation`.

Versioning
----------

The project version is stored in ``VERSION`` and injected into both binaries at
build time (``internal/options.VERSION``). Release ``0.8.0`` is documented
here. Two independent version numbers matter operationally:

* the **binary version**, exchanged with ``ServerGetVersion`` and shown by
  ``gonetem-console version``;
* the **Docker image version** (``IMAGE_VERSION``, currently ``0.6.0``), which
  the server appends to image names that have no explicit tag. Pin tags in the
  configuration to decouple image upgrades from binary upgrades.

Configuration written by older releases is generally accepted: unknown YAML
keys are ignored and missing keys fall back to built-in defaults. The
``.gnet`` archive layout is stable; see :ref:`project-format`.
